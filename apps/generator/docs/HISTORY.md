# План Generator, версия 2

Статус: черновик. Версия 1 (канва Вишапа) заменена этим документом.

## Что исправлено относительно версии 1

Формат спецификации
- `inputs` — объекты (`name`, `in`, `rule`), не строки.
- `must_never`, `should`, `may` — объекты (`id`, `text`). `id` уникален во всей спецификации.
- `updated` — ISO-дата (`YYYY-MM-DD`). Datetime и строки в другом формате отвергаются.
- Неизвестные ключи верхнего уровня и внутри элементов — ошибка с номером строки (ловит опечатки вроде `mustnever`).
- Повторяющиеся ключи верхнего уровня — ошибка.
- `caller` — кто вызывает: `public`, `signed-in`, `internal`. Для `http-endpoint` без него — критическая дыра.
- `output` — относительный путь со слешами `/`, без `..`, `.`, пустых частей, абсолютных путей и букв дисков. Проверяется ещё на загрузке спецификации.

Intake
- Требования берутся из `inputs`, `outputs`, `must_never`, `should`, `may`. В версии 1 из `inputs` и `outputs` ничего не бралось.
- Порядок ID: inputs → outputs → must_never → should → may. R1..Rn.
- `priority`: `must_never` — critical; `inputs`, `outputs`, `should` — high; `may` — medium.
- `source` — `{field, line}`, номер строки берётся из узла YAML, а не из индекса списка.
- Проверка способа: `inputs` — rule + test; `outputs` — test; `must_never` — rule + test; `should`, `may` — test. Analyzer не выбирается по требованию: он запускается на Verify для всего кода (решено 2026-10-28).

Design
- Gaps — выход Design, не отдельная стадия.
- `missing_input`, `contradiction` — critical. `assumption` — noted.
- Файлы: путь, интерфейс, требования, меры (auth, validation, rate_limit), library_check.
- Реализуется в шагах 3–4, не в текущем.

Build
- Тесты именуются `test_rN`.
- `ast.parse` и `ruff` обязательны до Verify. Ошибка по одному файлу не обрывает сборку всех: ошибка помечается на этом файле.
- LLM вызывается через провайдера, его интерфейс не придумывается здесь заранее.

Verify
- Три выхода: вердикт по коду, вердикт по спецификации (`stale: true` старше 90 дней от `updated`), `coverage`.
- Порог coverage 80%. Ниже — `needs_verification`.
- Вердикт по коду не может вынести модель, которая писала код.
- `run_pipeline` из Анализатора вызывается по его реальной сигнатуре (сверяется перед подключением), не по догадке.

Deliver
- Трасса: требование → код → тест → находка.
- `diff` против файла на диске. Считается до записи.
- `backup` перед записью, `vishap rollback ID` восстанавливает.
- Гейт (`--gate`) блокирует запись, если:
  - провален critical или high requirement,
  - coverage < 80%,
  - открыта `contradiction` или `missing_input`,
  - спецификация stale: true.
- Без `--gate` — запись есть, дыры и провалы в отчёте.
- `--force` с `--gate` — запись есть, в отчёте `forced: true`.
- Аудит: `skipped: [...]` перечисляет стадии, которые не запускались.

## Решения от 2026-10-28

LLM для Build
- Любой OpenAI-совместимый endpoint, не только Claude. Те же переменные, что в Вишапе: `VISHAP_LLM_PROVIDER=custom`, `CUSTOM_LLM_URL`, `CUSTOM_LLM_KEY`.
- Ключ только из окружения. Не в коде, не в git, не в отчёте.
- Клиент `llm.py` готов (ветка `stage-4-llm-client`), только стандартная библиотека. Адреса по умолчанию нет: `CUSTOM_LLM_URL` и `CUSTOM_LLM_MODEL` обязательны. `http` разрешён только для localhost (Ollama), иначе `https`. Ключ не попадает в ошибки и `repr`. Ответ больше 5 МБ отвергается.
- Проверен на подставном сервере (тесты) и 2026-10-28 на настоящей модели: DeepSeek, `https://api.deepseek.com`, `deepseek-flash`, запуск из PowerShell на ноутбуке. Из песочницы DeepSeek недоступен (прокси).
- 2026-10-28, первый прогон генерации на `deepseek-flash`: все 8000 токенов ушли на рассуждения, ответа не было. У DeepSeek рассуждения включены по умолчанию (`high`). Добавлены необязательные `CUSTOM_LLM_THINKING` (`enabled`/`disabled`) и `CUSTOM_LLM_REASONING_EFFORT` (`low`/`high`/`max`); отправляются, только если заданы.
- Ключ задаётся на сессию PowerShell, не постоянной переменной Windows: Вишап читает `.env` без перезаписи, и постоянная `CUSTOM_LLM_*` перебила бы его настройку.

Где запускается сгенерированный код в Verify
- Подпроцесс во временной папке с таймаутом. Не Docker.
- Это не изоляция. Код от модели запускается с правами пользователя ноутбука: может читать его файлы и ходить в сеть. Таймаут ограничивает только время. Перед запуском на чужих спецификациях это надо пересмотреть.
- Ещё не реализовано.

ruff и coverage
- `ast.parse` обязателен всегда.
- `ruff` и `coverage` запускаются, только если установлены. Иначе в отчёте `skipped` с причиной, и это не считается проходом.

## Безопасность (два решения)

1. Хеш материала на сервере. `material_hash` вычисляется от байтов спецификации на сервере. Клиентское значение не используется для кэша: иначе можно получить чужой результат или отравить кэш.
2. Пути вывода внутри корня. Каждый путь файла из плана резолвится (`resolve()`) и должен лежать внутри `output_root`. Абсолютные пути, `..` и симлинки, ведущие наружу, отвергаются до записи.

## Баги версии 1, учтённые в плане

- `design = design(requirements)` — затенение имени функции, `UnboundLocalError`.
- `intake(spec)` — функция принимала путь, а получала словарь.
- `avg_coverage` и `requirements` в консольном выводе не определены.
- `build`: `return {"error"}` внутри цикла прерывал сборку на первом сбое. Теперь ошибка привязывается к файлу.
- `generate_code`, `write_file`, `compute_diff` не определены.
- `critique_verdict` — угаданный ключ Анализатора. Реальный ключ сверяется по коду.
- `run_pytest` возвращал строку `"pass"`. Теперь возвращается структура с результатом и числом тестов.
- Гейт не учитывал дыры. Теперь учитывает (см. выше).
- `verify` сравнивал coverage по файлу, а не по требованию. Теперь coverage считается по требованиям, которые покрывает файл.

## Что реализовано сейчас

Шаги 1–2 (ветка `stage-1-2-intake`): `spec.py` — загрузка и проверка spec.yaml; `intake.py` — требования.

Шаг 3 (ветка `stage-3-design-gaps`, от шагов 1–2): `gaps.py` и `design.py`. Оба без LLM.

Gaps, правила по структурным полям:
- `missing_input`, critical: нет `target`, `kind` или `output`; `http-endpoint` без `caller`; у входа есть `rule`, а в `outputs` нет 400 или 422; вход без `rule` при `validate-inputs`.
- `contradiction`, critical: профиль `owasp-asvs-*` при `check: none`; одинаковый текст в `must_never` и в `should` или `may`.
- `assumption`, noted: вход без `rule` (любое значение принимается); нет `profile`; нет `check`; тесты для не-Python цели не планируются.

Чтение свободного `text` против требований — позже, с LLM. До того факт, сказанный только в `text`, считается отсутствующим. В `examples/spec.yaml` теперь есть `caller: public` (решено 2026-10-28). Без него «Called by the public web app» в тексте не засчитывается, и дыра критическая.

Design, план файлов для целей `python/*`:
- `__init__.py` в каждой папке пути вывода (role `package`);
- файл кода (role `code`): все требования, интерфейс из `kind`, `inputs`, `outputs`; меры `auth` (caller `signed-in`), `validation` (есть `rule` или `validate-inputs`), `rate_limit` (`id` правила содержит `rate-limit`); `library_check` — имена библиотек для сверки, сама сверка позже;
- `tests/test_<имя>.py` (role `test`): `test_r1`… для требований, где в способе проверки есть `test`.

Для `examples/spec.yaml`: 3 файла, 1 критическая дыра (нет ответа на неверный вход, 400 или 422). Решено 2026-10-28: это критическая дыра, не noted.

Шаг 4, часть без LLM (ветка `stage-4-build-checks`, от шага 3): `build.py`, функция `check_build`.
- Все файлы из плана на месте, лишних нет.
- `.py` разбираются `ast.parse`; ошибка — с номером строки.
- `ruff` — если установлен; если нет — `skipped`.
- В тестовом файле на каждое требование есть `test_rN` или `test_rN_<что угодно>`. Имена ищутся в дереве разбора, не подстрокой: `test_r10` не засчитывается за R1, имя в комментарии не считается.
- Тест с номером несуществующего требования — ошибка.
- Все проблемы собираются, одна плохая не прячет остальные.

Шаг 4, генерация (ветка `stage-4-generate`): `generate.py`, функция `generate_code`.
- Модель получает требования, план файлов, дыры и текст спецификации. Текст передаётся между маркерами как данные, не как инструкции.
- Ответ — один JSON `{"files": {"путь": "код"}}`. Обёртка в ```json``` допускается. Не JSON или не та форма — `GenerateError`.
- Ответ сразу проходит `check_build`. Файл вне плана — ошибка. Файлы не пишутся: это работа Deliver.
- Тесты требуются на `unittest`, чтобы запускаться без pytest.
- `scripts/try_generate.py` — проба на настоящей модели: печатает строки [Intake]/[Design]/[Build] и кладёт файлы в `.generated/<время>/` (в .gitignore).

Тесты: `python3 -m unittest discover -s tests -t .` — 98.

Не реализовано: генерация кода через LLM (Build), verify, deliver, API, CLI, чтение `text` через LLM, сверка библиотек.

## Первый прогон на настоящей модели (2026-10-28)

DeepSeek `deepseek-flash`, `CUSTOM_LLM_THINKING=disabled`, `examples/spec.yaml`.

- Build: 3 файла и 9 тестов, `check_build` — ok.
- Код: SQL параметризован (R4), ответ 400 на неверный ввод выбран и помечен `# assumption:` (G1), сырой ввод не логируется (R5), в ответе только id и name (R2).
- Баг в коде, не пойманный своими тестами: `re.compile(r"^[A-Za-z0-9]{1,64}$").match(...)` пропускает `alice\n`, потому что `$` совпадает перед последним переводом строки. Нужно `fullmatch` или `\Z`.
- Тесты, запуск на Windows: 8 из 9 прошли. Один упал из-за ошибки в самом тесте: `assertNotIn("", ...)` всегда ложно. Два слабых: `test_r4_parameterized` разбирает собственный исходник, в `test_r5` проверка `hasattr(user_mod, "print")` ничего не доказывает.
- `open()` без закрытия и без `encoding`: на Windows читается как cp1251.
- Ошибка Design: в `tests/` не запланирован `__init__.py`, поэтому `python -m unittest` без `discover -s tests` находит 0 тестов.

Вывод: `check_build` проверяет форму, а не правильность. Отличить баг в коде от бага в тесте — задача Verify: свои атакующие тесты (в том числе `\n` в конце значения), прогон в подпроцессе, правила и Анализатор.

Тесты проекта: `python3 -m unittest discover -s tests -t .` — 103.

## Этап 5: Verify (ветка stage-5-verify)

Что есть: `src/generator/verify.py` и `_sandbox_runner.py`. Три выхода: вердикт по коду, вердикт по спецификации (stale, если `updated` старше 90 дней), покрытие (меньше 80% даёт needs_verification).

Как проверяется каждое требование:
- тесты модели (unittest в временной папке);
- собственные атаки Verify: границы длины, пустое значение, пробел, кавычка, пунктуация и `имя\n` для query. Последнее ловит ошибку `$` + `.match` из первого прогона, которую тест модели пропустил;
- статические правила по AST: SQL из f-строки, `%`, `+`, `.format`; логирование данных запроса (`request`, `environ`).

Если тест модели падает, а собственные проверки Verify проходят, это needs_verification с пометкой «тест может быть неверным» (случай `assertNotIn("", ...)`).

**Важно: песочница не изоляция.** Код запускается подпроцессом с правами пользователя. Защита только в том, что окружение очищено от ключей, есть таймаут и `-X utf8`. Для недоверенного кода нужен Docker или похожее.

Пропускается, если не установлено: ruff, coverage (в отчёте «skipped»).

Design теперь планирует `tests/__init__.py` (иначе `unittest` находил 0 тестов) и знает `route` из спецификации.


## Этапы 5–8 (2026-10-28)

Analyzer (`analyzer.py`). Настоящий интерфейс Vishap: команда `vishap analyze FILE --quiet --sarif OUT` (из `src/cli.py` в conveyor_app), результат читается из SARIF. Каждый файл кода копируется во временную папку и анализируется отдельно. Уровень `error` проваливает код; нет команды — `skipped` с причиной; сбой или таймаут — `error`, и это `needs_verification`. Анализатор получает обычное окружение (ему нужен собственный ключ) и отправляет код своей модели.

Verify, добавлено: поле `notes` (ответ 500 на допустимый ввод; в песочнице нет базы), блок `analyzer`.

Deliver (`deliver.py`):
- гейт блокирует при: ошибках сборки; critical/high не `passed` (включая «не доказано»); провале Analyzer; покрытии ниже 80%; открытой critical-дыре; stale; проблемах Verify (не запустились тесты и т.п.). Покрытие `skipped` не блокирует;
- запись: временный файл рядом + `os.replace`; сбой посреди — откат всего прогона; symlink, `..`, абсолютные и дисковые пути отвергаются;
- манифест и backup в `.vishap/runs/<id>/`; id — 8 знаков хеша, коллизии в одну секунду разведены;
- откат отказывается, если файл изменён после прогона; повторный откат запрещён; созданные папки удаляются, если опустели.

Pipeline (`pipeline.py`): все этапы подряд. Раунды исправления: при проблемах Verify или сборки модель получает свои файлы и список проблем (между маркерами, как данные) и присылает файлы заново; по умолчанию 2 раунда. Анализатор запускается, только когда остальное прошло (дорогой вызов), и его находки тоже идут модели на исправление. Если вызов исправления упал, остаётся предыдущая версия.

CLI (`cli.py`), SARIF (`sarif.py`), REST API и форма (`server.py`, `web/index.html`): см. README. `--provider` из черновика не сделан: модель задаётся окружением, как в Vishap.

Отличия от черновика на холсте: холст описывал `vishap generate`; настоящая команда `vishap-generator generate`, чтобы не конфликтовать с Vishap.

Проверка без настоящей модели: `tests/test_e2e.py` запускает настоящий CLI против локального подставного сервера (запрос llm.py, окружение, коды выхода, файлы). На настоящей модели с исправлением и Анализатором ещё не запускалось.

Тесты проекта: 216 (на 0.1.1).

Без лишних вызовов модели: таблица STRIDE по spec (не по коду), `--strict`, поиск инструкций к модели в spec, секрет в spec как дыра, напоминания по области (`domain:`), `loss_pct` (модель недодала файлы), `--effort quick|standard|deep`, `--repro`, дополнения аудита в трассе. С вызовами модели, но с судьёй-исполнением: `--candidates N` (лучший из N по Verify), память раундов исправления с ранней остановкой, `--cove` (модель отвечает по spec, что должен делать сервис на странных значениях, код запускается на тех же значениях, ответы сравниваются).
- Что не взято: «самокритика» модели как проверка (мнение, не доказательство), голосование по тексту (оно показывает согласие, не правоту), цепочка рассуждений в отчёте.
- Новые ключи гейта: `strict_missing_pct`, `require_stride`, `fail_on_cove`, `max_loss_pct`. Новый промпт: `04_verify_cove`.
- Тесты проекта: 466. Настоящую модель не гоняли: COVE, кандидаты и промпты проверены на заглушке. Docker и CI не запускались.

## 0.6.1 (2026-10-28)

- Публичная демо-страница для Render: режим `GENERATOR_CHECK_ONLY=1` (только проверка спецификации, без модели и без запуска кода), `render.yaml`, раздел в `deploy/README.md`. Генерацию на публичном адресе не включали: она тратила бы ключ на чужих и запускала бы код по чужому тексту.

## 0.7.0 (2026-10-28)

- Атаки Verify и пробы COVE работают для входов в `body` (JSON-объект) и `path` (подстановка в маршрут), не только `query` и `header`. Два новых примера для формы. Из плана снят пункт «больше видов входов» в части body и path.

## 0.7.1 (2026-10-28)

- Один сервис Render для двух целей: `GENERATOR_PUBLIC_CHECK=1` оставляет открытой страницу и проверку spec, а генерация (`/api/generate*`, `/api/jobs`) идёт только с токеном. Ключ модели и токен хранятся на сервере (в панели Render), в репозитории их нет. `render.yaml` переписан под этот режим. Публичную генерацию без токена по-прежнему не включали.

## 0.8.0 (2026-10-28)

- Первый настоящий прогон (Sonnet 5.5 через слой совместимости Anthropic, на Render) прошёл, и по его результату сделано пять поправок. (1) Проба допустимого значения, на которую песочница не ответила (нет базы), раньше считалась `pass`; теперь `inconclusive`, в заметках как не доказанная, а ошибка в коде на допустимом вводе проваливает требование. (2) Среда (Python, библиотеки из плана) попадает в сообщение модели до сборки: на этом прогоне модель узнала, что Flask не установлен, только из упавшего первого раунда. В образ Docker добавлен Flask. (3) Комментарии `# assumption:` собираются в список (отчёт, трасса, страница). (4) Стоимость без заданных цен показывается как «not priced», не как $0. (5) Ключ гейта `require_analyzer` и явная строка в отчёте, что вердикт без Анализатора.
- Тесты проекта: 524. Настоящую модель с новым промптом не гоняли. Образ Docker не собирали.

- Из разговора «если бы генератором был я, а LLM — моим инструментом»: модель не судья, судит запуск. Добавлено: мутационная проверка тестов модели (код меняют по мелочи, смотрят, заметят ли тесты; `--mutants`, `GENERATOR_MUTANTS`, ключ гейта `min_mutation_score`), раунд усиления тестов в deep (принимается, только если всё проходит и оценка выросла), расхождения кандидатов на одних и тех же пробах, вопросы автору по дырам рядом с допущениями модели.
